# 域间路由意图综合调研报告

**副题**：意图驱动域间路由 · 路由/策略意图语义与合规 · 域间路由安全中的意图——三分局面与交叉缺口

> 调研范围：BGP / RPKI / BGPsec / ASPA / BGP CAR / SCION。证据口径：IETF 标准原文（RFC Editor / datatracker）一手核验、部署测量、既有确定性模拟实验（仅窄假设）。生成日期：2026-10-15。

## 摘要

域间路由"意图"不存在统一的端到端"表达—承载—核验"环路，现状呈现清晰的三分局面。其一，RPKI 家族的**单侧授权事实**——ROA/ROV 的"谁有权起源、谁有权传播"——是目前唯一密码学上可信、工程上可部署的意图位；其二，**声明式策略载体**（RPSL/IRR、BGP Community、BGP Roles/OTC、ASPA）表达力与语义碎片化并存，且部分可被劫持者伪造注入；其三，**广义 IBN 意图**（RFC 9315 意义上的期望输出、偏好、时变条件、分级保证）在跨 AS 域结构性缺失。本报告以三条调研线加交叉缺口分析给出证据化结论（G1–G5），并给出五条可操作课题建议；全部结论可追溯至证据日志与标准状态记录。

## 一、引言

### 1.1 背景与调研问题

BGP 是事实上的域间路由协议，既承载可达性信息，也通过属性与策略表达运营者意图[1]。域间路由安全的演进围绕"可验证性"展开：RPKI 以资源公钥基础设施提供来源授权基础设施[2]，ROV 基于 ROA 对收到的前缀—起源归属进行验证并给出 Valid / Invalid / NotFound 判决[3]，BGPsec 提供逐跳路径签名（协议规范见[4]，部署考量见[5]）。但"安全"与"意图"之间存在一个尚未被系统性回答的问题：**运营者想表达什么（intent），标准里有没有承载它的字段，又有没有办法核验它被遵守（compliance）**。

本报告围绕三条调研线展开：

- **Track A──意图驱动域间路由与 IBN**：域间是否存在类似 IBN 的端到端意图环路；
- **Track B──路由·策略意图语义与合规**：既有策略/授权载体各自表达什么语义、能否被核验、是否可伪造；
- **Track C──域间路由安全中的意图**：来源/所有权/路径授权意图在安全机制中的落位，以及"声明—行为"落差。

### 1.2 范围、方法与术语

范围为**域间（AS 边界）**的路由与路由安全意图，域内网管自动化只作对照。方法为三层证据：标准原文一手核验（RFC Editor / datatracker）、部署测量数据、既有确定性模拟实验（仅作窄假设证据）。术语见表 1-2-1-1。

| IBN（意图驱动网络） | 以意图为输入、持续保证期望状态的网络管理范式 | RFC 9315[6] |

## 二、Track A：意图驱动域间路由与 IBN

### 2.1 IBN 的定义与意图环路

RFC 9315 把意图定义为"期望输出（wanted outcome）"，把 IBN 定义为以该期望输出为输入、并通过持续保证（assurance）闭环维持该状态的管理范式[6]。其逻辑环路抽象出五部件——**表达（expression）/ 翻译（translation）/ 解析（resolution）/ 激活（activation）/ 保证（assurance）**，面向业务、策略、网络三个层次[6]。表 2-1-1-1 给出五部件与域间路由侧的对应关系。

表 2-1-1-1 RFC 9315 意图环路五部件及其域间对应

| 部件 | 功能 | 域间路由侧的"客体" |
| --- | --- | --- |
| 表达 | 声明期望输出 | 授权对象（ROA、ASPA）、策略载体（RPSL、Community、Roles） |
| 翻译 | 高层意图映射到底层配置 | ROA → 前缀授权、Roles 协商 → OTC 语义等 |
| 解析 | 在拓扑/约束中求可达方案 | 选路器（BGP bestpath） |
| 激活 | 下发并生效 | BGP UPDATE 与属性（OTC、Community 等） |
| 保证 | 验证实际状态与意图一致性 | 域间**缺失**（无统一 assurance 反馈） |

### 2.2 域内成熟度与域间缺口

域内（数据中心、园区、管理域广域网）的 IBN 已有较多实践：控制器、意图 API、闭环验证相对成熟。但在**域间**，不存在"一个意图对象 + 一个核验器"的组合：AS 边界上的意图碎片化地分散在证书库对象（ROA/ASPA）、BGP 属性（Community、Roles/OTC）与选路细节中，且分属不同信令平面。RFC 9315 的通用框架面向单域管理，尚未投射到跨安全域场景（Interpretation，支撑 §5.1 的 G4）。

### 2.3 域间"准 IBN"载体

#### 2.3.1 BGP Color-Aware Routing（BGP CAR）

RFC 9871 定义 BGP 颜色感知路由（CAR）：用颜色（Community 编码）区分服务意图（如低延迟 / 高带宽 / 备份路径），结合 AIGP 属性（RFC 7311，携带跨域聚合 IGP 度量并参与 bestpath 决策）实现跨域的意图感知选路[7][8]。CAR 是现有标准中**最接近"域间 IBN"的机制**：它把"服务意图"译成颜色，在跨域路径上传递并影响 bestpath 决策。但其意图粒度限于"颜色 → 流量工程偏好"，不覆盖授权/安全意图，且依赖增量部署与场景配置（Fact + Interpretation）。

#### 2.3.2 Segment Routing

RFC 8402 定义段路由（SR）架构：数据面显式携带路径指令（SID 列表 / SR Policy），能力上可表达"期望路径段"[9]。SR/SRv6 是灵活的**数据面路径携带与执行**机制，但缺少"意图声明 + 符合性核验"的闭环；其意图表达隐含在网络/策略编排层，与 RPKI 授权事实分属不同平面（Fact）。

#### 2.3.3 SCION

SCION 的 IRTF PANRG 概述草案（draft-dekater-panrg-scion-overview-06）描述数据面**显式路径段选择（path segments）**与路径策略表达：发送方在选择路径时表达对路径段的"意图"（如经过某隔离域、避开某中转）[10]。在现行 IP 互联网中，SCION 是唯一在数据面把"真路径意图"作为一等公民的载体；但它**仍是 Internet-Draft（非 RFC）**，且属协议堆栈级改造、尚未大规模部署（Fact + Interpretation）。

#### 2.3.4 小结：无统一端到端意图环路

对 IETF datatracker 的穷尽式名称检索（`name__icontains=asintent` → 0 命中；`as-intent` → 仅过期草案 draft-li-teas-intent-based-routing）表明：**IETF 不存在"统一 AS 路由意图对象"工作项**[11]。结合上文，**域间不存在端到端的"表达—承载—核验"意图闭环**，只有语义不统一、分属不同平面的准载体，对照见表 2-3-4-1。

表 2-3-4-1 域间"准 IBN"载体对照

| 载体 | 表达什么意图 | 承载平面 | 是否有核验闭环 | 状态 |
| --- | --- | --- | --- | --- |
| BGP CAR（颜色 + AIGP） | 流量工程 / 服务偏好 | BGP 属性 | 无（仅参与 bestpath） | RFC 9871，可用 |
| Segment Routing | 路径段指令 | 数据面 SID 列表 | 无 | RFC 8402，实施中 |
| SCION | 显式路径段选择 | 数据面 | 部分（路径认证） | I-D（非 RFC） |
| RPKI / ROA / ROV | 起源 / 上游授权事实 | 证书库 + BGP | 有（ROV） | RFC，已部署 |

## 三、Track B：路由·策略意图语义与合规

### 3.1 声明式策略载体：RPSL / IRR

RPSL 用 import/export 关系、路由谓词（filter）等表达运营策略声明[12]，RPSLng 扩展 IPv6 与多协议（MPLS/VPN）语义[13]。IRR 数据库承载这些声明。**问题在于认证性**：RPSL 本身无密码学签名机制，IRR 记录可由对象 owner 写入，劫持者可注入伪造策略声明；各 IRR 仓库口径不一，"多源共识"是事实上的自然修复（Fact：无签名机制；Interpretation：攻击面与合规风险）。

### 3.2 BGP Community 语义与注入攻击面

BGP Community 属性（RFC 1997）是跨域策略信令最早的载体之一[14]；BLACKHOLE Community（RFC 7999）定义 well-known 的直通黑洞语义[15]；Large Community（RFC 8092）把语义空间扩到 32 位[16]。语义碎片化的根源在于：除少量 well-known 外，绝大多数 Community 是私有/双边约定，**无统一注册表**；且**任何 UPDATE 均可携带任意 Community**——劫持者可注入伪 Community 向全网发出错误策略信号，构成"声明层可注入"的典型攻击面（Fact：属性格式无认证；Interpretation：攻击面风险）。要点见表 3-2-1-1。

表 3-2-1-1 BGP Community 语义要点

| 载体 | 表达语义 | 认证性 | 注册 / 一致性 | 引证 |
| --- | --- | --- | --- | --- |
| BGP Community | 跨域策略信令（过滤/隧道/标签/选路偏好等） | 无（可注入） | 无统一注册表 | RFC 1997[14] |
| BLACKHOLE | 目的地址黑洞（RTBH 协作） | 无 | well-known + 私有 | RFC 7999[15] |
| Large Community | 32 位扩展语义空间 | 无 | 无统一注册表 | RFC 8092[16] |

### 3.3 路径 / 关系意图：Roles、ASPA 与 AS_SET 弃用

**BGP Roles + OTC**。RFC 9234 引入 BGP Roles：AS 在 OPEN 中协商各自角色（Provider / Customer / Peer / Route-Server / Route-Reflector 等），UPDATE 携带 Only to Customer（OTC）属性（属性码 35），供接收方识别并**丢弃违反角色约定的路由**，用于路由泄漏的预防与检测[17]。角色约定是对等关系意图的显式声明，但其声明在 OPEN/每会话内、无密码学签名（Fact）。

**ASPA**。自治系统提供商授权（ASPA）把来源意图从"起源"扩展到"**谁被授权作为我的 provider / 我的路由可经由哪类邻居传播**"。验证算法草案为 draft-ietf-sidrops-aspa-verification（rev 28）[18]，对象 profile 草案为 draft-ietf-sidrops-aspa-profile（rev 29）[19]——**截至 2026-10-15，两个组件均为活跃 Internet-Draft、尚未实现 RFC**（应特别注意：其验证算法与 RFC 9319 无关，RFC 9319 是 maxLength 的 BCP，见 §3.4）。ASPA 依据 ROA/ASPA/AS_PATH 给出 Valid / Invalid / Unknown 判定，设计上刻意只编码 provider 关系以保持可判定性；但其仍是"授权集合"而非"偏好/排序"，且只表达**单侧有向边（顾客 → 上游）**，不存在"接收偏好"反向维度（Fact + Interpretation，支撑 §5.1 的 G2）。

**AS_SET 弃用**。RFC 9774 弃用 AS_SET 与 AS_CONFED_SET（Obsoletes RFC 6472），摘要明确指出这两者与 RPKI-ROV（RFC 6811/6907/9319）的起源 AS 歧义有关[20]——这是"语义清爽化"方向的新旁证：弃用会带来模糊语义的机制，以支撑更精确的授权 / 路径核验。

### 3.4 来源授权意图：ROA / ROV / maxLength / RTR

ROA（Route Origin Authorization）是"前缀 → 被授权起源 AS"的密码学声明对象。现行 profile 为 RFC 9582（Obsoletes RFC 6482）[21][22]；ROV 依据 ROA 对收到的 BGP 路由判决 Valid / Invalid / NotFound[3]；运行操作规范 RFC 7115 给出从判决到路由决策的映射与 NotFound 处理建议[23]；**maxLength 粒度**由 RFC 9319（BCP 185）专门约束——建议限制 ROA 前缀集、除特定场景外避免 maxLength，以缩小"伪造起源子前缀劫持"的攻击面，体现"授权粒度表达力 ⇔ 伪造面"的张力[24]；RPKI-to-Router（RTR）协议供路由器拉取 ROA 状态与增量同步[25]。Track B 机制承载汇总见表 3-4-1-1。

表 3-4-1-1 Track B 机制承载汇总

| 机制 | 表达意图 | 信令平面 | 验证目标 | 认证性 | 状态 | 引证 |
| --- | --- | --- | --- | --- | --- | --- |
| RPSL / IRR | 策略 / 过滤声明 | 注册库（库外） | 无（不参与转发） | 无签名 | RFC 2622/4012 | [12][13] |
| BGP Community | 跨域策略信令 | BGP 属性 | 无 | 可注入 | RFC 1997/7999/8092 | [14][15][16] |

## 四、Track C：域间路由安全中的意图

### 4.1 来源 / 所有权意图与"强锚"

RPKI 从资源证书出发、以签名对象表达"**谁有权起源、谁有权传播**"的授权事实[2]。其中 ROA/ROV 是目前唯一"密码学上可信、工程上可部署"的意图位——它是**单侧授权事实（单向、快照式、可验证）**：运营者声明可验证、全业界可核验（Fact）。

**BGPsec 的定位**：RFC 8205 提供逐跳路径签名、RFC 8206 给出部署考量[4][5]。BGPsec 验证的是"路径确实按宣告逐跳走过"——属于**运行时路径证明**，并不表达"运营者想怎么走"的意图语言。因此本报告将 BGPsec **明确排除在"意图载体"定义之外**（Fact + Interpretation），这是方法学上的重要裁剪。

### 4.2 行为面：路由泄漏

RFC 7908 定义并分类 BGP 路由泄漏（泄漏类型、场景、检测困难）[26]。从意图视角看，泄漏的本质是**声明（角色 / 关系约定）与实际转发不一致**：一方声称"只向顾客传播"，实际却把路由传播给了错误邻居或跨泄漏到不期望的中转。角色与意图的"行为面证据"由此而来——但 RFC 7908 只做问题定义与分类，**不提供意图声明与检测反馈的闭环**（Fact，支撑 §5.1 的 G4）。

### 4.3 声明—行为落差（部署测量）

依据 LARUS Foundation / APNIC 2026 年初发布的 RPKI 部署测量数据[27]，见表 4-3-1-1。

表 4-3-1-1 RPKI 声明—行为落差测量

| 指标 | IPv4 | IPv6 |
| --- | --- | --- |
| ROA 覆盖（声明侧：Valid 占比） | 60.3% Valid / 37.7% Not Found / 2.0% Invalid | 60.9% Valid / 36.1% Not Found / 3.0% Invalid |
| 有效 ROV 部署（行为侧：实际执行核验） | ≈ 6.5%（测量 AS 占比） | 同左 |

| triz-feedback-01 | ROV / prefix-hijack（×3） | 0.7917 | 0.0187（conv 88.93 / v-lat 1.34） | disputed / inconclusive |

证据来源与口径详见既有报告《域间路由意图全景调研-结论速览》[28]与《RPKI承载域间路由意图-调研报告》[29]。这些实验支持的方向性判断是：**声明式意图验证能显著提升劫持检测（0.55–0.79，误报率 ≤ 0.02 量级）**，但可判定性与表达力争衡明显，且未在真实网元（FRR/VPP）上复现，故仅作课题设计的输入，不作广泛结论。

## 五、交叉缺口与课题建议

### 5.1 交叉缺口 G1–G5

表 5-1-1-1 交叉缺口分析

| 缺口 | 描述 | 关键证据 | 主要对应线 |
| --- | --- | --- | --- |
| G1 声明盲区 | ROA 声明覆盖过半（≳60%）但有效 ROV 部署 ≈6.5%，声明与核验行为严重脱节 | RFC 7115、部署测量[27] | ③② |
| G2 单侧 vs 双向语义 | ASPA 一条有向边（顾客 → 上游）表达授权，但"接收偏好 / 排序"维度结构性缺失 | [18][19] | ②③ |
| G3 广义意图结构性不支持 | 偏好 / 排序 / 时变 / 条件无承载字段；maxLength 体现"粒度 ⇔ 伪造面"张力 | RFC 9319[24] | ② |
| G4 无保证闭环 | SHOULD（声明层）与 IS（行为层）无一致性检查与反馈；RFC 9315 的 assurance 部件未投射到跨安全域 | RFC 7908[26]、RFC 9315[6] | ①③ |
| G5 权威层级混合 | 声明权威层级混杂（RPKI 认证 vs IRR 未认证 vs Community 可注入），"多源共识"是事实上的自然修复 | §3.1–§3.2、datatracker 检索[11] | ②③ |

### 5.3 课题建议

1. **锚定分级 + UNKNOWN 显式建模**：把"声明 / 行为 / 核验"三层映射到 ROV 判决状态机（Valid / Invalid / NotFound → Unknown），对 G1 的声明盲区做显式指标（发布覆盖 vs 有效核验执行）。
2. **双向意图边**：在意图图层面补"顾客 → 上游"传播授权（对应 ASPA 语义）与"接收偏好 / 排斥"两类有向边；ASPA 观察先行（即便未 RFC 化，其算法可按草案独立验证），对 G2。
3. **意图合规 / 漂移指标**：定义 intent-compliance 与 drift 度量，把 SHOULD↔IS 差距量化到可监测（对 G4）；RFC 7908 泄漏分类可作为行为面判据集合[26]。
4. **显式 BGP-Community 注入攻击面风险**：把"公共策略信令可被劫持者注入"纳入威胁模型与检测（异常 Community 组合、双边约定白名单），对 G5[14][15][16]。
5. **保持表达模型可翻译**：跟踪 ASPA 转 RFC、RFC 9871、SCION path-authentication 三条外部线，把课题的意图模型做成**可映射到标准资本的开放 schema（open schema）**，避免自闭环方言（对 G3）。

## 六、结论

### 6.1 一句话结论

**域间路由意图不存在统一的端到端"表达—承载—核验"环路**，三分局面稳定成立：① 单侧授权事实（ROA/ROV/ASPA 的密码学授权）是唯一强锚；② 声明式策略（RPSL、Community、Roles/OTC）是弱载体，语义碎片化且部分可注入；③ 广义 IBN 意图（RFC 9315 意义上的期望输出）在跨 AS 域结构性缺失。机制侧没有出现"统一路由意图对象"工作项[11]，缺口集中在声明盲区（G1）、单向语义（G2）、广义语义无条件承载力（G3）、无保证闭环（G4）与权威层级混合（G5）。

## 七、局限

1. 调研以标准原文与公开测量为主，未对真实网元（FRR/VPP）做意图表达一致性实验。
2. ASPA 与 SCION 相关文档为 Internet-Draft，状态快照会随 IETF 推进变化（截至 2026-10-15：ASPA 双 I-D 未 RFC 化；SCION overview 非 RFC）。
3. RPKI 部署测量源自 LARUS/APNIC 聚合口径，抽样与口径差异可能影响绝对数。
4. 实验侧证据（RouteEngineSim）为窄假设、全部 disputed，不构成广泛调研的充分证据。
5. "意图"语义学上存在主观性，本报告采用 RFC 9315 的 operational 定义，未处理意图识别/哲学面。
6. Community / RPSL 的"真实部署语义"依赖全网观测，本报告未做流量级语义反演。
7. datatracker 检索为名称级（`name__icontains`），未覆盖全文级意图检索；如后续接入全文知识库（如 WeKnora RFC 全集）可作为扩展。
